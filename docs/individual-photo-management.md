# Individual photographs and image optimisation — release 009

This release extends the committed HEIC repair at `a2cf028`. Individual bulk photographs now have an import inbox and independent catalogue links. Editors can archive/restore an item, explicitly split a legacy grouped photograph, regenerate images and review permanent deletion. Admin → Deletion progress provides recovery after an interrupted deletion.

Splitting creates one uncatalogued child per original, preserving source IDs, byte hashes, sizes and Storage paths. Derivatives, image sets, per-source attempts and file-specific transcriptions follow the source. Shared title, date, place, people, notes, recollections, comments and item provenance stay on the archived parent context; they are not automatically copied to children. Front/back views of one object must remain grouped. Splitting is explicit and cannot be reversed through the UI.

Archive/restore does not remove bytes. Permanent deletion requires an archived item, Editor access, a reviewed version, typed DELETE and acknowledgement. SQL blocks unreviewed dependencies, live/recent preview work and deletion of a context with children. Once deletion starts, the item is hidden and new content writes are blocked; it cannot be restored. Storage is removed in batches with checkpoints before database cleanup. Retry through Deletion progress after a failure. A minimal actor/time/item-ID/count audit remains. Use permanent deletion only for material deliberately approved for removal.

## Image delivery

The immutable master remains in its private bucket. A responsive image set contains a progressive JPEG display (quality 80, maximum edge 2400), WebP thumbnail (1200), small WebP (600) and tiny real WebP placeholder (24). Images retain aspect ratio without upscaling. Output is generated separately; originals are never overwritten. New sets retain previous derivative versions. Regeneration is explicit, Editor-only and may create another set even if bytes match.

Cards use responsive thumbnails, lazy loading and placeholders; detail/catalogue pages prioritize their first display. Private asset GETs check authentication/RLS and return `private, no-store`, with no shared Next image cache or public signed URL. Cover/portrait references resolve through the derivative route. Read-only diagnostics report stored dimensions, bytes and auth/database/Storage timings. `scripts/audit-image-delivery.sql` audits existing receipts; `scripts/measure-image-delivery.js` measures currently rendered derived images in a signed-in browser. Neither starts conversion or downloads masters.

The recovered upstream sample measurement (718,114-byte HEIC) produced a 1280×854 JPEG of 287,570 bytes, 1200×801 WebP of 194,914 bytes, 600×400 WebP of 54,680 bytes and 182-byte placeholder in 567ms locally. These are sample measurements, not production performance guarantees or measurements of either family original.

## Production readiness and release order

Migration `202611010009_item_management_and_image_sets.sql` is complete and validated locally. Existing migrations 001–008 are unchanged. The standard release baseline is the installed 001–008 schema, including bulk migration 007 and attempt tracking 008. The full baseline with audio 006 was tested; do not infer remote migration state from the repository. Review the production migration history and take the normal database/Storage recovery snapshot before release.

009 adds lifecycle/grouping columns, image-set/current-set metadata, management/deletion audit tables, RLS, restricted RPCs and a manifest-scoped Storage DELETE policy. Installation does not split, archive or delete historical items, generate previews, or modify existing Storage objects. It does add default column values and rebuild derivative uniqueness constraints. This is a schema/policy change, not a data repair script.

Apply only missing, reviewed migrations in order, then deploy this code through the normal manual workflow. New catalogue/image queries require 009; do not deploy the code first. Keep all buckets private, existing authentication and public client configuration, the Node preview runtime and its 60-second budget. No new secret or dependency is needed. Regeneration, splitting and deletion must wait until old in-flight application requests have drained. Do not casually roll back to code using legacy `reserve_display` after responsive sets exist: 009 permits multiple display versions per source. Forward repair is safer than dropping schema or deleting historical derivatives.

Local validation establishes release readiness on the tested baseline; hosted Supabase Storage, Vercel/Linux decoding and physical iPhone/Safari remain release acceptance checks. No remote migration, production data change, push or deployment was performed. See [final validation](validation.md) and [exact files to commit](item-management-commit-manifest.md).

## Exact manual production smoke test after deployment

1. Before applying 009/deploying, record the existing grouped item's ID and both originals' IDs, filenames, byte sizes, SHA-256, bucket and Storage path. Use the read-only audit SQL if helpful. Confirm the migration history, backup/recovery snapshot and private bucket settings. Do not re-upload or alter these sources.
2. After the reviewed migration and deployment, sign in as an Editor/Admin. Open the existing item and Manage item. Confirm both originals are listed and the item remains grouped. If only legacy derivatives exist, choose **Regenerate display images and thumbnails** once; otherwise reuse the stored sets. POST `/api/v1/previews/<original-id>` should return 200 and an image set. On failure capture `requestId`, `stage`, `code` and the matching function log; wait 75 seconds after interrupted preview work before retrying.
3. Inspect `current_image_sets` and file receipts read-only. Each original must have a stored set linked to the correct item with display JPEG ≤2400px and two WebPs ≤1200/600px, plus a placeholder. Previously stored derivatives remain. In Network, `/api/v1/assets/<variant-id>` returns the expected MIME, dimensions and `Cache-Control: private, no-store`; no master request should be needed for rendering stored images. Use **Measure stored image delivery** to capture bytes/timings without starting conversion.
4. Check detail, Explore, import inbox (for a batch item), catalogue page and reload on desktop and a physical iPhone/Safari. Confirm orientation, colour, complete aspect ratio, visible placeholder/loading transition, responsive `srcset` and lazy loading below the fold. Download both original files intentionally and compare byte sizes/SHA-256 with step 1; they must match exactly.
5. Archive the chosen item. Confirm it leaves active Explore and ordinary member access; Editors find it under **Archived items**. Restore it and confirm it returns with the same files/context. Test a Viewer and a Contributor: they cannot invoke Editor split/archive/delete/regenerate controls or RPCs. Contributors retain permitted own-item catalogue/preview actions.
6. Only if the owner intends to separate the existing photographs: review **Split photographs into separate items**, type SPLIT and acknowledge the context policy. Confirm exactly one child per original, each with an independent catalogue link; source IDs/paths/hashes and derivatives are preserved. The archived parent retains shared context and links to children. Edit one child's title/date/place/people/context and verify the other child stays unchanged. Do not split front/back views of one physical object, and do not perform this irreversible step merely to test the release.
7. Exercise permanent deletion only on an explicitly approved disposable item in a test archive, never either family original. Archive it, wait at least 75 seconds after preview activity, review counts/files, type DELETE and acknowledge. Confirm controls require both confirmations. For recovery testing, deliberately interrupt the browser request after submission, then use **Admin → Deletion progress** if the operation remains pending; otherwise record that cleanup completed. Resume until no pending deletion, item/file/image-set/content rows or corresponding Storage objects remain. Confirm other items/people survive and the minimal deletion audit remains. Controlled Storage failure recovery was tested locally; do not change production policies to manufacture an outage.
8. Sign out. Private detail/management pages must redirect to sign-in; asset/preview/original APIs and direct private Storage must deny unauthenticated reads. Sign back in and confirm stored sets display without decoding again. For the next intended bulk import, verify one item per separate photograph, retained batch context and independent catalogue edits; no extra family uploads are required for the existing-item repair.

If a hosted check fails, retain diagnostics and stop destructive management operations. Do not delete/re-upload masters or rerun installed migrations as a workaround.
