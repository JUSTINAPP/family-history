# Archival audio recordings

## Implemented workflow

**Add → Voice recording** opens `/add/voice` for a standalone oral history. An existing item has **Add a voice recollection** beside its written recollections. Recordings have real browser Record, Pause/Resume, Stop, local Preview, Delete/Start Again and explicit Save controls, plus an existing-file picker. No microphone audio is uploaded before Save. The old spoken demo remains only in explicit demo mode; live photograph capture points to the real recording flow after preserving the photograph.

Recording uses `getUserMedia` and `MediaRecorder`, with runtime MIME negotiation: WebM/Opus, MP4 or Ogg according to browser support. Elapsed time excludes pauses. Tracks are released after Stop and on navigation/unmount, including late permission responses. Capture requests unprocessed audio where the browser supports those constraints, but hardware/browser capture and codec choices still affect the recording. The saved master is the exact original browser-generated file, not a subsequent conversion. Nothing is sent to a third-party recording service.

M4A/MP4 audio, MP3, WAV, WebM and Ogg are supported up to **30 MiB per original**, matching the existing file model and Storage limit. The client checks size, MIME/container signatures and SHA-256 before direct private Storage upload. After that upload, an authenticated Node endpoint downloads the reserved object, checks byte size/hash/signature and parses the local container using music-metadata, rejecting unrecognised/audio-less/video files. Only then does the application call the receipt finalisation RPC. No AI service is connected.

The SQL RPC independently enforces permissions, links, reservations and Storage size/MIME receipts. As with the photograph contract, SQL does not decode or cryptographically re-hash object bytes: a custom native/API client must follow the validation/finalisation contract. The Node validation endpoint is not a service-role-only attestation system; no service-role key is introduced. Checksums establish submitted-byte integrity, not authenticity of a speaker or historical claim.

Save is metadata-free: the default title is “Voice recording”, or speaker/date when provided. Browser recordings can fill their known recording date; imported files retain an unknown recorded date unless supplied, without confusing it with their upload date. Optional details include title, reported speaker, a separate historical Person link, date certainty, location, context, tags, related people and archive items. Related links can be added/edited later. Retry retains the capture UUID and checks the reserved hash, avoiding overwrite/duplicates. After an interrupted attempt the entered details are held for retry; edit them after the source is preserved, or explicitly select a new source. Selected files and unfinished retries live in this tab, not an offline/reload-resumable inbox. A local download link lets users keep a recording before saving.

## Model and permissions

Only **202610310006_audio_recordings.sql** is new. Migrations 001–005 are unchanged. Migration 005 has already been applied to the live project (confirmed by the user). Do not rerun it, reset the database or change existing sources.

- `archive_item_files` stores audio with purpose `audio_original` and bucket `archive-audio`, alongside the existing UUID path, filename, MIME, size, SHA-256, uploader and timestamp fields. There is still no ordinary client UPDATE/DELETE policy for source objects. The browser's original MIME including codec parameters is retained separately on the recording; Storage uses the validated base media type.
- `recollections` and `recollection_audio` retain the existing item → recollection → original-file structure. Each attached recording gets its own recollection/file, so different members can contribute independently. A standalone oral history also creates an `archive_items` row of kind **Audio**, with a normal Explore/detail route. Audio-only items use a restrained microphone image in Explore.
- New nullable/defaulted recording columns hold speaker/date/context/tags/duration, idempotency identity, edit actor/time and soft-archive state. `audio_people` and `audio_item_links` hold archive-scoped links with composite FKs, explicit SELECT grants, ENABLE/FORCE RLS and no direct user DML. Metadata RPCs validate all target archives.
- Active Contributors can create recordings and edit their own unarchived recordings. Editors/Admins can edit, archive and restore accessible recordings. Viewers/Commenters may listen to stored active recordings but cannot create/edit them. Changing a verified standalone item's catalogue assertions requires an Editor and returns the changed assertion to reported status. Historical Person records remain separate from Members.
- Audio metadata changes append provenance; finalisation records the original receipt/hash and an activity event. Written recollections already present are not changed. A narrow read RPC supplies contributor display names for readable recordings without exposing profile emails or changing profile RLS. Initial contextual words remain on their attributed recollection even if the recording's catalogue description is edited later.
- Archiving hides a recording and its Storage access from ordinary members; Editors can still inspect and restore it. Standalone archived oral-history items also leave ordinary Explore results. Archiving never deletes bytes. Editors can restore through the recording edit route retained in browser history/its URL; a general archived-recordings management inbox is not implemented.

The nullable `recollection_audio.manual_transcript` leaves a simple future manual-transcript path. The existing transcriptions table can reference audio source files for future machine drafts/reviews. There is no transcription interface, machine transcript, transcript search or external AI request in this pass.

## Private playback

Inline native audio controls provide play/pause, seek and position/duration where the codec/browser exposes them; autoplay is off. The existing authenticated file route checks the file row with the user's RLS session, then issues a **10-minute private Storage signed URL** for audio only. Supabase serves byte ranges directly, avoiding Vercel response-size limits and allowing native seeking. Downloads request the preserved original filename. Images keep their existing private response path, with single-range response support added.

Signed links are temporary bearer capabilities, not public bucket URLs. A link already issued can remain usable until its ten-minute expiry after access is revoked/archived. New requests require membership again. Private/no-store responses prevent shared application caching. Players have a “Refresh private playback” action that obtains a fresh link and retains playback position where practical. A browser that cannot decode an original format can download it to a suitable player; no playback transcode/derivative is currently generated. A future derived playback asset must be a separate file linked to the original.

## Manual Supabase / deployment action

1. Review and run **only `supabase/migrations/202610310006_audio_recordings.sql`**, once, in the existing project's SQL Editor or your normal tracked migration process. It adds audio metadata/link tables/RLS/RPCs and extends the existing private audio bucket's MIME allowlist. It widens the archive-item kind constraint to include Audio without removing data. It replaces narrowly scoped read helpers/policies so archived audio remains private. No existing source object is deleted or converted.
2. No additional bucket, secret, service-role key, recording provider or AI configuration is needed. `npm ci` installs the local parser. Keep the Node runtime for `/api/v1/audio/:id/complete`; the route allows 60 seconds for validation. Original uploads go directly to Supabase, not through a Vercel request-body upload.
3. Review the [combined commit manifest](audio-commit-manifest.md), commit manually when ready and deploy through the existing GitHub/Vercel process. **The agent did not apply 006, stage, commit, push or deploy anything.** No hosted data was changed.

## Deployment smoke test

1. On desktop, Add → Voice recording: record, pause/resume, stop, preview and save with all optional fields blank. Reload Explore and play/seek through the new oral history. Download the original and compare its SHA-256.
2. Open an existing photograph, add a voice recollection and then a separate written recollection. Confirm both persist after reload and the photograph/HEIC preview is unchanged.
3. Upload M4A, MP3 and WAV examples. Verify speaker/date/context, duration where available and seek playback. Retry an interrupted save on the same page without duplicate files/items.
4. As the owner Contributor edit the recording's metadata and link a person/another item. A different Contributor and a Viewer must not edit it; a nonmember must not obtain a playback link. As an Editor edit, archive and restore it, confirming the master remains unchanged.
5. On an actual iPhone/Safari, check permission allow/deny, microphone selection, pause/resume, Stop final chunk, interruptions/background/screen lock, M4A/WebM compatibility, duration and seeking. Repeat a larger file through production Vercel/Supabase and refresh a playback link after expiry.

Local automated tests use disposable PostgreSQL, synthetic audio and a synthetic Web Audio stream feeding the real MediaRecorder; they never record a real microphone or upload test material into Supabase. Physical iPhone/Safari and hosted end-to-end validation remain required. If a browser interrupts recording, the UI stops/keeps available chunks where possible; it cannot guarantee capture while the OS suspends the page. Keep the page open and preview before saving.
